# Consistency review of the XN-Interact baseline

Baseline: *XN-Interact — Bun-Native Universal OAuth Social MCP Gateway*, prepared 2026-11-19.
Reviewed against: the XN-Bridge source in `~/code/XN-Bridge` as observed on 2026-11-19.

Each finding names the conflict, the resolution, and where the resolution is enforced. "Checker" means `bun run plan:check` (`scripts/plan/check.ts`), which fails when the plan data drifts from the resolution.

| ID | Conflict in the baseline | Resolution | Enforced by |
|---|---|---|---|
| CR-01 | Tool names use dots (`social.auth.connect`). The Anthropic tool-name pattern and XN-Bridge's own tools use `[a-zA-Z0-9_-]`; dotted names risk rejection or silent rewriting by hosts. | Wire names are snake_case (`social_auth_connect`). The dotted name stays as `spec_name` for traceability and must map 1:1 (`.` → `_`). Host acceptance is measured in P0-05 before ADR-019 is accepted. | Checker `TOOL_NAME`; CORE-11; P0-05, P1-04, P1-10 |
| CR-02 | One concept has several spellings: `partial_success` (13.2) vs `partially_succeeded` (9.1); `approval_required` vs `app_approval_required` (13.2); per-target `published` vs non-publish operations; `OUTCOME_UNKNOWN` vs `unknown_outcome`. | Canonical enums in `plan/catalog.json`: run states, step states and target outcomes are lower-case states; error codes are upper-case. Target outcomes are operation-neutral (`succeeded`, not `published`). Provider review is `app_approval_required`; human approval is a separate error code. | `catalog.enums`; CORE-12 drift test (P1-03) |
| CR-03 | Error categories (`auth, approval, unsupported, rate, cost, validation, unknown`) cannot express policy refusals, provider failures or idempotency conflicts. 13 non-available capability states had no error codes. | 10 categories, 26 error codes. Every capability state except `AVAILABLE` maps to exactly one code. Every code carries a `bridge_error_class` so the host can report it to XN-Bridge without guessing. | Checker `CAPABILITY_ERROR_MAP`, `BAD_ENUM`; INT-04 |
| CR-04 | Section 4 skill files (`content.publish-one.json`, `engagement.moderate.json`) do not match the skill IDs in 8.2, and `engagement.moderate` is not a skill. | A manifest file name equals its skill ID (`skills/content.publish.one.json`). Moderation is the `hide` action of `engagement.respond`. | P6-02 loader rejects mismatched names |
| CR-05 | Only two workflows were named (`oauth.connect`, `content.crosspost`) while skills and write tools need durable definitions. | Nine workflows with explicit steps (`oauth.connect@1`, `auth.disconnect@1`, `content.publish@1`, `content.media_publish@1`, `content.crosspost@1`, `content.schedule@1`, `content.mutate@1`, `engagement.respond@1`, `ops.recover@1`). Each is used by a tool, a skill or a fan-out. | Checker `UNREFERENCED_WORKFLOW`, `ROUTE_COVERAGE` |
| CR-06 | Side effects were free text ("Conditional", "approval where required", "may incur quota"), which neither a router nor XN-Bridge can classify. | Every operation, tool, skill and workflow has a risk class aligned with XN-Bridge (`READ`, `LOCAL_WRITE`, `EXTERNAL_WRITE`) plus a side-effect class. Tool risk equals the maximum of its operations. `social_content_update` always needs approval (fail closed). `social_workflows_execute` is `EXTERNAL_WRITE` with per-skill approval so XN-Bridge classifies it conservatively. | Checker `RISK_MISMATCH`, `SIDE_EFFECT_MISMATCH`, `APPROVAL_POLICY` |
| CR-07 | 6.1 says every write tool needs a preflight plan reference; journey 17C has one publish call doing preflight itself. | Consequential tools are two-phase. `mode=plan` returns `plan_id`, `plan_hash`, preview and `approval_id`. After the human approves in the CLI, `mode=execute` with `plan_id` and `operation_id` consumes the approval atomically. This matches XN-Bridge's prepare → approve → begin pattern. | Checker `TWO_PHASE`; FLOW-10; P4-07, P4-09 |
| CR-08 | P5 performs an approved real write, but approvals and the intent journal only arrive in P7. | A minimal write-safety kernel (plan builder, approval authority, intent journal) moves into P4. P7 generalizes it to fan-out, scheduling and recovery. | Task dependencies P5-04 → P4-07, P4-08 |
| CR-09 | `social.media.upload` and `social.content.create` mixed local staging with provider-side writes outside any approval. | Release 1: both are local-only (`LOCAL_WRITE`). Provider uploads (`media.upload`) and provider drafts happen only inside approved, journaled workflows. | Checker `DIRECT_EXTERNAL_WRITE` |
| CR-10 | "Journal before side effects" and "reconcile unknown writes" were prose rules. | Structural invariant: every step with an external-write operation has an earlier `approval_gate` (or inherits one through fan-out), is immediately preceded by `journal_intent`, and is followed by a `reconcile.read` step. | Checker `UNGATED_WRITE`, `UNJOURNALED_WRITE`, `UNRECONCILED_WRITE` |
| CR-11 | 9.3 offers "refuse a second process or add leases". The owner runs both Claude Code and Codex, so two stdio processes will share one home. | SQLite worker leases with heartbeat and expiry; reads run in any process; a step executes only under a held lease. | FLOW-11; P2-08, P7-05 |
| CR-12 | `content_drafts.owner_account_id` conflicts with a cross-platform draft that has many targets. | Drafts are account-independent; target accounts are bound in the immutable plan. | P2-02 schema, P4-05 |
| CR-13 | The persistence model had nowhere to keep a pending PKCE verifier, no lease table, and an `approvals` table without operation, content digest, nonce or actor evidence. | Added `oauth_attempts` (encrypted verifier), `execution_plans` (immutable plans for two-phase tools), `worker_leases`, `schema_meta`; `approvals` gains `operation`, `content_digest`, `nonce`, `actor_evidence`, `consumed_by`. Secret-bearing tables declare encrypted columns. | Checker `ENCRYPTION`; P2-02 |
| CR-14 | "Skill" means three different things across the systems involved. | *Gateway skill*: JSON manifest in `skills/`, run deterministically by XN-Interact. *Host skill*: `SKILL.md` read by Claude Code or Codex (`xn-social`, in `host-skills/`). *Xninetzy skill*: loaded through `skill_get`. Documents always qualify the word. | This document; PB-02 |
| CR-15 | Counts and names repeated in prose drifted between sources (22 vs 31 tools). | `plan/catalog.json` is the single source for tools, skills, workflows, enums, error codes, resources, prompts and tables. The implementation is tested against it. | CORE-12; P1-03 drift test |
| CR-16 | Scheduled publishing conflicts with approval expiry. | The approval is consumed when the schedule is registered and binds the plan to a due-time window. A content change needs a new approval. Every scheduled response states the process-lifetime caveat. | FLOW-08; P7-07 |
| CR-17 | The skill selection key `{operation, media_kind, target_count}` ignored scheduling, and ties were only caught at runtime. | Three dimensions including `scheduled`, with priority and specificity. The checker proves every combination resolves to exactly one skill. | Checker `ROUTE_GAP`, `AMBIGUOUS_SKILL`; SKILL-05 |
| CR-18 | The baseline does not mention XN-Bridge. | Host-mediated integration: neither server calls the other. XN-Bridge maps 20 `social.*` capabilities to XN-Interact tools, classifies all 22 tools, and coordinates a new `social` domain. See [xn-bridge-integration.md](xn-bridge-integration.md). | INT-01…INT-11; phase PB; checker `BRIDGE_*` |
| CR-19 | Two approval systems would exist (XN-Bridge Ed25519 approvals and XN-Interact CLI approvals). | XN-Interact is authoritative for social writes. Release 1 is dual-gate: XN-Bridge's approval gates its bookkeeping, XN-Interact's gates the provider call. Neither substitutes for the other. Federation is a later option after a threat model. | Checker `APPROVAL_AUTHORITY`; INT-03, INT-07, INT-10 |
| CR-20 | XN-Bridge's unattended autonomy is global in code (`executions.py`), but its AGENTS.md scopes it to career. | XN-Interact never treats bridge autonomy as approval. XN-Bridge should gain a capability allowlist so `social.*` never runs unattended (owner decision, PB-11). | INT-03, INT-08 |
| CR-21 | XN-Bridge approval targets must be http(s) URLs with a host (`security.origin_of`), but social targets are plans across accounts. | Target `https://xn-interact.invalid/plans/{plan_id}`. `.invalid` is reserved (RFC 2606) and never resolves; bridge dedupe then works per plan. | Checker `APPROVAL_TARGET` |
| CR-22 | Phase gates would be unsatisfiable when later phases still cover the same requirement (for example OAuth per provider in P8). | A requirement in a gate may only be covered by tasks in that phase or earlier. Per-provider requirements gate at release. | Checker `GATE_UNSATISFIABLE` |
| CR-23 | The Definition of Done lacked the XN-Bridge connection and named no specific host. | Release sign-off (P10-09) depends on PB-14 (real provider through XN-Bridge) and PB-13 (cross-server recovery); hosts are Claude Code and Codex. | Task P10-09 dependencies |
| CR-24 | The baseline asserts MCP revision 2026-07-28 support in SDK v2 under Bun. Not verified here. | Observed on 2026-11-19: `@modelcontextprotocol/server` 2.4.0 is the latest on npm; Bun 1.4.0 is installed. The negotiated revision and optional extensions are measured in P0-04 and claims stay unverified until then. | SC-08, SC-09; P0-04 |
| CR-25 | Rollback strategies assume version control, but the repository is not a git repository. | P0-18 initializes git; commits only when the owner asks. | Task P0-18 |
| CR-26 | The baseline removes the AI-callable confirm tool but nothing stops one from reappearing. | No tool may contain `confirm` or end in `_approve`/`_grant`; tools mentioning approvals must be `READ`. The tracker applies the same rule to itself: only the owner, at an interactive terminal, can move a task to `APPROVED`. | Checker `SELF_APPROVAL_TOOL`, `SELF_APPROVAL` |
| CR-27 | Found while activating: for the Claude host, XN-Bridge `discover` put the project `.mcp.json` in the host fingerprint but `capability_resolve` did not, so every project-scope provider (osm, careers-crawl, gmaps, gmail-send, xn-interact) resolved as `HOST_CONFIG_CHANGED` through MCP. | Both paths now load the bridge repository `.mcp.json` for the Claude host. | PB-18; docs/integration/bridge-acceptance.md |
| CR-28 | Found by the cross-server test: the Python MCP SDK turns a JSON-looking string into an object, so `evidence_register(content=<JSON>)` was rejected. | `content` accepts an object or list and stores canonical JSON. | PB-18; XN-Bridge `test_evidence_register_accepts_json_tool_output` |
| CR-29 | XN-Bridge routing was a static Python table: every new domain or capability needed code, and `route_intent` and `capability_resolve` could disagree. | One router composed from code, `defaults/intents.toml` and `data/config/intents.toml`, a capability index over every registered capability, and live provider resolution with the same fingerprint. Routing evaluation keeps 0 confident errors. | PB-17; INT-12 |
| CR-30 | Found in the provider docs: callback requirements differ. LinkedIn documents only an HTTPS redirect; TikTok desktop documents loopback and a hex-encoded PKCE challenge, while the broker assumed loopback and base64url for everyone. | `OAuthProfile` gains `redirect` and `pkce_encoding`; the broker sends the right challenge and refuses an HTTPS-only provider with `UNSUPPORTED` until the HTTPS callback (P8-08) exists. | tests/oauth/profiles.test.ts; docs/providers/linkedin.md, tiktok.md |
| CR-31 | Instagram publishing requires media on a publicly accessible server, which conflicts with a sandbox that never serves or fetches remote media. | Open decision for the owner: host media somewhere public or skip Instagram media publishing. Instagram stays UNVERIFIED. | docs/providers/instagram.md |
| CR-32 | Found by a stress test of AUTH-07: a reader holding old tokens could start a second refresh with an already-rotated refresh token and wrongly mark a healthy account `needs_reauth`; two processes sharing one home could do the same, because the provider rotates before the local database commits; `App.close()` was not idempotent. | Revision re-check before refreshing, a per-grant refresh lease across processes, re-reading the grant before treating a refresh rejection as reauth, idempotent close. The fixture's transactions are atomic so tests cannot create the same symptom. | tests/oauth/oauth.test.ts (25 burst rounds, 15 two-process rounds); P3-05 |
| CR-33 | Found by a concurrency test of FLOW-03: ten concurrent `execute` calls with the same `operation_id` sent 20 provider writes instead of 2. The run lease is per process, so several `advance()` calls in one process all passed it and read the step as pending before any of them marked it running. Production exposure: the 2-second ticker or a status poll running while `execute` is still in flight. | `advance()` is single-flight per run inside a process, and a step is claimed with a compare-and-swap `UPDATE ... WHERE status IN (pending, ready, waiting_provider)` before any await, so even with leases disabled in both processes only one executor reaches the provider. | tests/workflow/concurrency.test.ts; mutation test: removing the claim gives 4 writes instead of 2 |

## Unchanged decisions

Everything not listed above stands as written in the baseline: Bun + TypeScript, official SDK v2, modular monolith, stdio default, `bun:sqlite`, `Bun.secrets` with fail-closed fallback, Zod at boundaries, 22 tools as a benchmark hypothesis, static tools plus lazy capability resources, declarative skills, durable workflows, separate approval channel, OAuth code + PKCE, optional loopback HTTP only after audit, no browser fallback, honest scheduler lifetime, and client-independent benchmarks (ADR-001 to ADR-018).

## Facts, inferences and unknowns

- Verified by reading source: XN-Bridge tool list, risk classifier semantics (first match, fail-closed `EXTERNAL_WRITE`), approval statement fields, `origin_of` URL rule, error classes, outcome and evidence enums.
- Verified by command: Bun 1.4.0 installed; npm registry reports `@modelcontextprotocol/server` 2.4.0, `@modelcontextprotocol/sdk` 1.32.2, `zod` 4.6.7.
- Inference: dotted tool names may be rejected or rewritten by hosts (CR-01). P0-05 confirms or refutes it.
- Unknown: every provider capability. All seven evidence rows are `UNVERIFIED`.
